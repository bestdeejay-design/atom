# Как собрать Atom Lite

Два пути. Первый — облачный (рекомендуется), второй — локальный.

---

## Путь 1: сборка в облаке GitHub (рекомендуется)

Настроено в `.github/workflows/build.yml`. Тебе не нужно ничего
устанавливать у себя — сборка идёт на машинах GitHub, для публичных
репозиториев это бесплатно.

### Как запустить

1. Запушь что-нибудь в любую ветку репозитория **или** зайди в
   **Actions** → **Сборка Atom Lite** → **Run workflow**
2. Дождись окончания (первый прогон — 30–60 минут)
3. Открой завершённый прогон и скачай артефакт внизу страницы:
   - `atom-macos-x64` → `atom-mac-x64.zip` — для Intel Mac
   - `atom-macos-arm64` → `atom-mac-arm64.zip` — для Apple Silicon

### Установка скачанного

```bash
unzip atom-mac-arm64.zip -d /Applications
xattr -dr com.apple.quarantine /Applications/Atom.app   # снять карантин
open /Applications/Atom.app
```

Локально собранный и скачанный из CI архив помечен карантином, потому что
не подписан сертификатом Apple. `xattr` это снимает.

> ⚠️ Сборка **не подписана**. Для личного использования это нормально.
> Если захочешь подписать — нужен сертификат Apple Developer, и тогда
> сборку запускают с флагом `--code-sign`.

## Путь 2: сборка на своём Mac

### Что нужно

| | Версия | Почему |
|---|---|---|
| Node.js | **12.16.3** | Именно под неё писались скрипты (npm 6, node-gyp 5) |
| npm | 6.14.x | Идёт в комплекте с Node 12 |
| Python | **3.9** (не 3.12+) | В Python 3.12 убрали `distutils`, на котором ломается старый node-gyp |
| Git | любая | |

### Apple Silicon: важный нюанс

**Node 12 не существует для arm64.** Он выпускался только под x64.

Отсюда два варианта:

**Вариант «A» — x64-сборка, работает через Rosetta 2**

```bash
nvm install 12.16.3
nvm use 12.16.3
script/bootstrap
script/build --compress-artifacts
```

Получится интеловский `Atom.app`. На M-чипе он запустится — но через
Rosetta 2, то есть не нативно.

**Вариант «B» — нативная arm64-сборка**

Нужен Node **16 или новее** (у них есть сборки для arm64) и явное указание
целевой архитектуры:

```bash
nvm install 16
nvm use 16

export npm_config_arch=arm64
export npm_config_build_from_source=true

script/bootstrap
script/build --compress-artifacts
```

Тогда `electron-packager` скачает Electron для arm64,
`electron-mksnapshot` — arm64-версию mksnapshot, а нативные модули
скомпилируются под arm64.

> Это путь с неизвестными: скрипты сборки 2022 года официально
> тестировались только на Node 12. Если что-то падает — не удивляйся,
> это ожидаемо, и это чинится по шагам (см. ниже).

## Что именно было починено для Apple Silicon

Оригинальный Atom собирался только под Intel. Три причины, все найдены в коде:

### 1. Архитектура была прописана константой

```js
// script/lib/package-application.js — было:
arch: process.platform === 'darwin' ? 'x64' : HOST_ARCH, // OS X is 64-bit only
```

Комментарий «OS X is 64-bit only» писался до появления Apple Silicon.

**Стало:** новая функция `computeTargetArch()` в `script/config.js` — берёт
архитектуру машины, а переопределяется через `npm_config_arch` или
`ATOM_TARGET_ARCH`.

### 2. Имя V8-снапшота было жёстко x86_64

```js
// script/lib/generate-startup-snapshot.js — было:
// TODO: check if we're building for arm64 and use the arm64 version of the binary
destinationPath = path.join(..., 'v8_context_snapshot.x86_64.bin');
```

Electron на macOS ищет снапшот строго по имени:
`v8_context_snapshot.x86_64.bin` для Intel и
`v8_context_snapshot.arm64.bin` для Apple Silicon.

**Стало:** имя выбирается по `CONFIG.targetArch`.

### 3. Хорошая новость: Electron 11.5.0 всё умеет

Проверено — в релизе `electron/electron@v11.5.0` есть все нужные артефакты:

```
electron-v11.5.0-darwin-arm64.zip        ✅
mksnapshot-v11.5.0-darwin-arm64.zip      ✅
chromedriver-v11.5.0-darwin-arm64.zip    ✅
```

Переписывать проект не нужно. Нужно было только починить сборку.

### 4. gyp-генератор `make` не передаёт компилятору `-arch`

Даже когда apm просит node-gyp собрать под arm64 (`--arch=arm64`,
`npm_config_arch=arm64`), на macOS это ни на что не влияет: node-gyp собирает
через gyp-генератор `make`, а в его шаблоне Makefile нет ни одного `-arch` —
только

```
CFLAGS.target ?= $(CPPFLAGS) $(CFLAGS)
LDFLAGS.target ?= $(LDFLAGS)
```

Архитектуру выбирает сам clang, и здесь начинается неприятное: clang,
запущенный из x64-процесса (наш Node 12 работает под Rosetta), по умолчанию
целится в `x86_64`. Проверено в CI: `clang` из нативного shell даёт `arm64`,
а тот же `clang` из Node x64 — `x86_64`.

**Стало:** `script/lib/run-apm-install.js` добавляет `-arch <цель>` в
`CFLAGS`/`CXXFLAGS`/`CPPFLAGS`/`LDFLAGS` — но только для зависимостей
приложения и только при кросс-сборке. Собственные модули apm и зависимости
`script/` должны остаться под архитектуру сборочного Node: их запускает
Node 12 (x64), под arm64 они просто не загрузятся.

### 5. Бинарники получаются «универсальными» — ужимаем их

Из-за той же двойственности (процесс x64, цель arm64) clang собирает файлы с
двумя срезами сразу: `x86_64 arm64`. Работать это будет, но в приложении лежат
срезы под чужую машину, а размер растёт.

**Стало:** `script/lib/thin-native-modules.js` после копирования ассетов
проходит по `.node` в `out/app/node_modules` и делает `lipo -thin <цель>`.
Модули, в которых целевого среза нет, не трогаются — их ловит проверка в CI.

### 6. Дамп символов не нужен

Символы (`.sym`) собирались только для краш-репортера — по ним он разворачивал
стек перед отправкой на серверы Atom. В этой сборке отправлять некуда и некому.
Заодно шаг был хрупким: `minidump` не умеет бинарники с двумя архитектурами.

**Стало:** `script/build` пропускает дамп символов (включается флагом
`--dump-symbols`), а архив символов собирается, только если каталог есть.

### 7. Встроенный менеджер пакетов (apm) убран из приложения

`apm` — единственная крупная часть Atom, которая не могла стать нативной:
он запускается **своим** Node 12, а не Electron, поэтому внутри приложения
лежал ещё один бинарник Node (36 МБ, x64) вместе с 67 МБ зависимостей
(из них 33 МБ — собственный npm 6). Под Apple Silicon это работало через
Rosetta и только ради загрузки пакетов из сети.

**Стало:** при упаковке `apm` больше не копируется в бандл
(`script/lib/package-application.js`), команда `apm` не устанавливается в
`/usr/local/bin` (`src/command-installer.js`), а сам apm остался инструментом
сборки — он по-прежнему ставит зависимости приложения в `script/bootstrap`.

Что это даёт: **≈ 103 МБ распакованного веса**, в приложении не остаётся ни
одного компонента не под arm64, а сборка перестаёт тащить в бандл второй Node.

Как ставить пакеты в такой редактор: положить папку пакета в
`~/.atom/packages` (Atom подхватывает оттуда всё при запуске) или добавить
пакет в сборку — тогда он окажется у всех, кто её поставит. Если однажды
понадобится именно `apm`, укажите путь к своему экземпляру в настройке
`core.apmPath` — редактор будет звать его, как раньше.

### 8. «Диета»: что не попадает в приложение

Вес приложения после переезда на arm64 — 495 МБ, из которых 273 МБ приходилось
на `app.asar`. Разбор показал, что заметная часть — не редактор, а его
обвес: расширение DevTools для разработки (28.6 МБ вместе с зависимостью),
предсобранный кэш стилей (29.5 МБ) и тестовые библиотеки (19 МБ).

**Стало:**
* `script/lib/include-path-in-packaged-app.js` — фильтр упаковки не пускает в
  приложение пакеты, которых в нём быть не должно (список с причинами — прямо
  в файле);
* `script/build` — предсобранный кэш LESS больше не создаётся: первый запуск
  соберёт стили сам и положит их в `~/.atom/compile-cache/less`;
* спецификации в собранном приложении больше не запустятся — тестовые
  библиотеки возвращаются переменной `ATOM_LITE_KEEP_TESTS=1` (см.
  `docs/WEIGHT-RU.md`).

### 9. Темы: `dajet` и `joer`

В сборке четыре своих пакета тем — две пары «интерфейс + подсветка»;
по умолчанию включена `dajet`. Темы проверяются до сборки:

```bash
node script/check-themes.js
```

Скрипт собирает темы тем же LESS 2.7, что несёт сам редактор, проверяет
договор с чужими пакетами (56 имён интерфейса и 30 имён подсветки), а также
что ни одна переменная CSS не читается без объявления. В сборке этот шаг
стоит перед долгой сборкой — ошибка в теме ломает окно целиком, а стоит
секунды. Подробности — `docs/THEMES-RU.md`.

## Если сборка падает — где смотреть

| Симптом | Причина | Что делать |
|---|---|---|
| `Python is required to build Atom` | нет Python или он 3.12+ | поставить Python 3.9 |
| `node-gyp` ошибки на нативных модулях | несовпадение ABI | `export npm_config_build_from_source=true` |
| `Could not find mksnapshot` | скачался mksnapshot не той архитектуры | проверить `npm_config_arch` |
| В приложении модули `x86_64` | clang под Rosetta целится в x64 | `-arch` в `CFLAGS` (см. `run-apm-install.js`) |
| `minidump`: «more than one architecture» | универсальные бинарники | дамп символов выключен (краш-репортов нет) |
| `Atom.app` не запускается сразу после сборки | карантин / не найдён снапшот | `xattr -dr com.apple.quarantine` |
| Падает на `git+https://github.com/atom/...` | сеть | архивы `atom/*` доступны, проверь соединение |
| В приложении нет команды `apm` | так и задумано: менеджер пакетов не поставляется (см. выше) | пакеты — файлами в `~/.atom/packages` |

## Полезные команды

```bash
script/bootstrap                    # установить всё необходимое
script/build                        # собрать
script/build --compress-artifacts   # собрать + сделать zip
script/build --install /Applications  # собрать + сразу установить
script/build --existing-binaries    # пересобрать без повторной транспиляции
script/lint                         # проверить стиль кода
script/test                         # прогнать тесты
node script/check-themes.js         # проверить темы (LESS и договор переменных)
```

## Что уже удалено из сборки

Пакеты `github`, `metrics`, `exception-reporting`, `open-on-github`,
`update-package-dependencies` исключены из `package.json` — они больше не
устанавливаются и не собираются. Вместе с ними ушли авто-обновление и
краш-репортер (осталась сама обработка падений). Подробности и цифры —
в `docs/WEIGHT-RU.md`.

Встроенный менеджер пакетов (`apm`, ≈ 103 МБ) в приложение больше не
копируется — см. раздел 7 выше.
