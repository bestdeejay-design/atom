## Короткий ответ

**Главный вес уже снят.** Это были пакет `github` (56 МБ `node_modules`:

### Куда двигаться дальше (диета 2.0)

Сейчас фильтр упаковки работает по **чёрному списку**: мы перечисляем то, что в
приложение не пускаем. Из-за этого остаются «хвосты» — зависимости удалённых
библиотек (например, `@sinonjs/*` от `sinon`). Полностью решает задачу
**белый список**: на этапе сборки считать дерево зависимостей от `package.json`
и от встроенных пакетов (у них свои `dependencies`, которые npm считает
посторонними — яркий пример `spelling-manager`) и копировать в приложение
только его. Тогда лишнее исчезает само, без ручного перечисления.

### Как это сделано (пункты 1–3)

**Исключения при упаковке** — `script/lib/include-path-in-packaged-app.js`.
Этот фильтр решает, что из `node_modules` попадает в приложение, а что нет.
Каждое исключение снабжено комментарием с причиной; список проверен поиском
`require` по `src`, `packages` и `spec`.

**Кэш LESS** — в `script/build` отключён шаг `prebuildLessCache()`. Это была не
функциональность, а ускоритель первого запуска: рабочий кэш всё равно живёт в
`~/.atom/compile-cache/less` (`src/less-compile-cache.coffee`), а папка в
приложении служила лишь резервным источником. Первый запуск после этого
собирает стили на месте — это секунды, и только один раз.

**Тесты и отладка — убраны из зависимостей совсем (диета 2.0).** Сначала эти
пакеты просто не кладутся в приложение, но `npm ci` всё равно ставил их в
`node_modules`, а вместе с ними тянулись их хвосты: 311 записей в замке, среди
которых оказался даже `dugite` — целый git от пакета `github`. Теперь их нет в
`package.json`, а из замка вычищено всё, до чего не осталось пути:

| Убрано из зависимостей | Почему |
|---|---|
| `mocha`, `mocha-junit-reporter`, `mocha-multi-reporters`, `chai`, `sinon`, `jasmine-*`, `mock-spawn` | нужны только спецификациям |
| `dalek` (встроенный пакет) | прогонщик тестов пакетов; его же `require` убран из генератора снапшота |
| `devtron`, `chart.js` | отладка и графики; ни одного `require` в коде |

**Измерено локально** (та же версия npm 6, что в apm): установка стала
**690 пакетов / 233 МБ** вместо **846 пакетов / 305 МБ** — минус 156 пакетов и
**72 МБ** ещё до упаковки. Заодно bootstrap стал быстрее: меньше качать и
собирать.

**Измерено в сборке** (прогон 38654131707, шаг «Диета — состав приложения»):
все 20 проверяемых имён отсутствуют, все 19 нужных на месте; дерево
зависимостей приложения — 502 пакета / 245 МБ вместо 256 МБ.

**Честно про вес приложения.** Архив почти не изменился (144.2 → **144.1 МБ**),
`app.asar` — 208.4 → 208.7 МБ. Причина: большая часть убранного и раньше не
клалась в приложение (тестовые библиотеки и devtron исключались фильтром
упаковки), а `moment` вернулся (+4.6 МБ). Что реально ушло из приложения —
≈ 16 МБ: `es-abstract` 5.8, `highlight.js` 2.4, `requirejs` 1.2, `@sinonjs` 1.1
и хвосты. Так что вторая часть диеты — это выигрыш не в размере архива, а в
устройстве: установка на 72 МБ легче, замок без 311 чужих записей, и найденная
ошибка с `moment`.

Чистку замка делает `script/prune-lock-orphans.js`: он обходит замок от
объявленных зависимостей по тем же правилам, что Node (свои вложенные → вложенные
родителей → верхний уровень), и проверяет, что у каждой оставшейся записи каждое
требование разрешается. Запуск: `node script/prune-lock-orphans.js`
(без `--write` — только показать, что уйдёт).

Что нужно знать: тесты Atom (`script/test`) теперь не запустятся — для них
библиотеки придётся поставить обратно (`npm i --no-save mocha chai sinon …`,
полный список — в комментарии `// ATOM LITE` в `package.json`).

**Возвращён `moment`.** В первой части диеты он был исключён из приложения как
«зависимость chart.js и winreg» — и это была ошибка: `moment` читает пакет
`notifications` (`lib/notifications-log-item.coffee`), без него падал бы журнал
уведомлений. Теперь он снова в сборке (+5 МБ), и в сборке есть проверка состава
(шаг «Диета — состав приложения»), которая следит, что он на месте.

### Что это значит на практике

Оптимизация имеет смысл **не ради размера на диске**, а ради:

1. **Скорости старта** — меньше пакетов грузится при запуске
2. **Памяти** — меньше процессов и модулей в куче
3. **Простоты** — меньше строк в списке языков и тем
4. **Автономности** — это уже сделано, и это главное

## Про `spell-check` — ответ найден

Вопрос был: «орфография — это нативная от ноутбука или сетевая?»

**Ответ: полностью нативная от macOS. Сети — ноль.**

Вот код `spell-check/lib/system-checker.js`:

```js
const spellchecker = require('spellchecker');

// We also force the use of the system or operating system library instead of Hunspell.
if (env.isSystemSupported()) {
    instance = new spellchecker.Spellchecker();
    instance.setSpellcheckerType(spellchecker.ALWAYS_USE_SYSTEM);
    ...
}
```

`ALWAYS_USE_SYSTEM` на macOS означает обращение к системному `NSSpellChecker` —
**тому же движку, что в Pages, TextEdit и Mail**. Никаких загрузок словарей.

Проверено на уровне исходников нативного модуля `spellchecker@3.7.1`:
- есть `src/spellchecker_mac.mm` — реализация через `NSSpellChecker`
- в модуле лежит Hunspell и словарь `en_US` на **2.1 МБ** — это **резервный
  вариант для других платформ**. На macOS при `ALWAYS_USE_SYSTEM` он не используется
- ни одного сетевого вызова в исходниках модуля нет

**Что это значит для тебя:**
- ✅ Работает со всеми языками, установленными в macOS
- ✅ «Выучить слово» пишет в системный словарь macOS
- ✅ Ноль сетевой активности
- ✅ **Оставляем** — это ровно та автономность, которая нужна

Единственный нюанс: `spellchecker` — нативный модуль, его нужно будет
пересобрать под arm64. Компилируется из C++ с Objective-C++ для macOS,
так что это стандартный случай.
