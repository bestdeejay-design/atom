# План: полностью нативный редактор для macOS

> ⚠️ **Этот документ частично устарел.** Решения от 2026-10-15 зафиксированы в `docs/adr/` (ADR-0001…0006) и в `docs/FEATURE-LIST-RU.md`. Главные отличия: **ничего не импортируем из Atom** (ни код, ни ассеты, ни настройки, ни палитры), вводится **концепция тишины** (ADR-0003), плагины — папки с разрешениями (ADR-0004). Разделы 2 и 5 ниже в части импорта больше не действуют.

**Статус:** черновик для обсуждения. Код не написан, решения ниже предлагаются, а не приняты.
**Исходная точка:** форк Atom «Lite» (см. `docs/HANDOFF-RU.md`): Electron 11, Apple Silicon, офлайн, темы `dajet` и `joer`.

---

## 1. Цель и принципы

**Цель:** быстрый, тихий, нативный редактор кода и текста для Apple Silicon Mac: SwiftUI/AppKit, без Electron, без Node, без CoffeeScript. Он должен ощущаться как Mac-приложение: горячие клавиши macOS, системный ввод текста (IME), VoiceOver, Liquid Glass, системные словари.

**Принципы, которые переносим из Lite:**

1. **Автономность по умолчанию.** Редактор не выходит в сеть без явного действия пользователя. Это принцип, а не технический долг. Исключение для ИИ-функций обсуждается в разделе 6.
2. **Вес и минимализм.** Не тащим то, что не используется. Каждую зависимость обосновываем.
3. **Свой стиль.** Палитры `dajet` и `joer` переходят в нативную систему тем. Визуальный язык сохраняем, код темы другой.
4. **Всё в git и в документах.** Решения фиксируются в `docs/`, как в остальных волнах.

**Что не переносим:** сам движок Atom (DOM-рендеринг через etch, first-mate, Node API, пакетная система на CoffeeScript), apm, dugite, Electron-шелл, снапшоты V8, Azure-пайплайны.

### 2.2. Идеи и поведение (переписываем на Swift)

| Идея из Atom | Что делаем в новом редакторе |
|---|---|
| **Command registry** (`src/command-registry.js`): команды с именами `editor:move-to-line` | Сохранить **именованные команды** как основу. Всё: меню, палитра, горячие клавиши, ИИ-инструменты и тесты вызывают одну и ту же команду |
| **Keymap со селекторами** (`atom-keymap`) | Сохранить модель «сочетание → команда в контексте». Контекст выражаем через предикаты Swift (фокус, язык, режим), а не CSS-селекторы |
| **Decorations** (`src/decoration-manager.js`) | Аналог: слой аннотаций поверх текста (подсветка, ошибки LSP, git-диффы, курсоры другого участника). Одна модель для всего |
| **Buffer + cursors + selections** (`src/text-buffer`, `src/cursor.js`) | Ядро модели: буфер с диапазонами, мульти-курсоры, undo-группы. Переписать на Swift с нуля |
| **Восстановление файлов** (`src/main-process/file-recovery-service.js`) | Автосохранение несохранённых буферов в `Application Support` и восстановление при сбое. Переносим идею, код новый |
| **Git-статус и диффы** (`src/git-repository.js`, `packages/git-diff`) | Полоса изменений в гаттере. Источник данных: `git` CLI или libgit2 |
| **Поиск и замена** (`find-and-replace`, `fuzzy-finder`) | Переписать. Поведение (регистр, регулярки, предпросмотр) взять из UX Atom как референс |
| **Пакеты и API расширений** | Отложено. Сначала ядро. Если вернёмся, то как отдельный этап с новым API (см. раздел 7) |

### 2.3. Что точно не нужно

- `apm` и реестр пакетов atom.io (мёртв, см. `docs/AUDIT-RU.md`).
- Встроенный Node/Electron, снапшоты V8, `script/lib/*` для упаковки Electron.
- Dugite/git-бинарь внутри приложения: используем системный `git` из Xcode CLT, если он есть.
- Старые языковые пакеты CoffeeScript/TextMate, если переходим на tree-sitter (см. раздел 3).

## 3. Тренды, которые закладываем в архитектуру

Ниже тренды 2026 года, которые влияют на решения. Для каждого указано, что с ним делаем.

### 3.1. GPU-рендеринг текста и отказ от веб-движков

Главный пример — Zed. По данным его 1.0 (апрель 2026), редактор написан на Rust, рисует через Metal на macOS и использует собственный UI-фреймворк GPUI, без Electron и Chromium ([programming-helper](https://www.programming-helper.com/tech/zed-editor-2026-ai-native-code-editor-performance), [petronellatech](https://petronellatech.com/blog/zed-editor-setup-guide-2026/)). Тот же путь проходил и Atom: его наследник как раз ушёл от Electron. Ссылки на цифры производительности в статьях противоречивы, поэтому в проекте не опираемся на них, а меряем сами.

**Решение:** ядро пишем на Swift, отказываемся от веб-технологий. Для первой версии текст рисуем через **TextKit 2 / AppKit**, а не через собственный Metal-рендерер. Причина: IME, VoiceOver, поиск по тексту, системная проверка орфографии уже работают. Собственный Metal-слой — отдельный этап, если замеры покажут, что TextKit 2 не тянет большие файлы.

### 3.2. Liquid Glass и новый дизайн macOS

Apple в macOS 26 (Tahoe) ввела материал Liquid Glass для элементов управления и навигации. Для AppKit есть `NSGlassEffectView`: contentView кладётся внутрь стеклянного слоя, геометрия синхронизируется через Auto Layout ([WWDC25, AppKit](https://developer.apple.com/videos/play/wwdc2025/310/)). Для SwiftUI есть `glassEffect`, `GlassEffectContainer` и `glassEffectID` для морфинга ([WWDC25, SwiftUI](https://developer.apple.com/videos/play/wwdc2025/323/)). В WWDC26 добавили концентричность углов (`NSView.LayoutRegion`, новый API для concentricity) и фиксированный scroll edge effect ([WWDC26](https://developer.apple.com/videos/play/wwdc2026/289/)).

**Решение:**
- Стекло только для плавающих элементов верхнего уровня: тулбар, боковая панель, панель ИИ. Текст редактора стекло не покрывает. Это прямая рекомендация Apple.
- Минимальная версия macOS: **macOS 26**. Это даёт `NSGlassEffectView` и новый дизайн. Цена: меньше пользователей. Решение владельца (раздел 8).
- Поддерживаем «Уменьшить прозрачность» и «Повышенный контраст». Палитры `dajet` работают как fallback.

### 3.3. Tree-sitter вместо регулярных грамматик

Zed и большинство современных редакторов парсят код через tree-sitter, а не через регулярные выражения (first-mate, который использует Atom). Структурный разбор даёт подсветку, фолдинг, навигацию по символам и основу для ИИ-контекста ([inithtml](https://en.inithtml.com/tools/zed-editor-the-lightning-fast-code-editor-with-deep-ai-integration-and-real-time-collaboration/)).

**Решение:** tree-sitter через Swift-биндинги и готовые грамматики для 13 языков Lite. TextMate-грамматики из `language-*` используем как справочник по scope-именам, не как рабочий код.

### 3.4. Протоколы ИИ-агентов: ACP и MCP

Новый стандарт — **Agent Client Protocol (ACP)**: JSON-RPC 2.0, который связывает редактор с ИИ-агентом, как LSP связывает редактор с языковым сервером. Создан Zed в 2025 году, поддерживается JetBrains. **MCP** связывает агента с инструментами и данными. Протоколы дополняют друг друга, а не конкурируют ([danilchenko.dev](https://www.danilchenko.dev/posts/agent-client-protocol/), [ayautomate](https://www.ayautomate.com/blog/agent-client-protocol-vs-mcp)). По состоянию на 2026 год Gemini CLI, Claude Code (через адаптер), Codex CLI, Goose и GitHub Copilot CLI работают через ACP ([morphllm](https://www.morphllm.com/agent-client-protocol)).

**Решение:** в редакторе реализуем **ACP-клиент** (агент — отдельный процесс, общение через stdio). Агенты подключаются по конфигу пользователя. MCP-серверы редактор передаёт агенту. Так редактор не привязан к одной модели, и это совпадает с принципом «автономность»: пользователь сам решает, какой агент запускать и откуда он берёт модель.

### 3.5. Edit prediction и агентное редактирование

Zed и другие редакторы показывают предсказание следующей правки (inline next-edit) и агентное редактирование с ревью изменений ([inithtml](https://en.inithtml.com/tools/zed-editor-the-lightning-fast-code-editor-with-deep-ai-integration-and-real-time-collaboration/)).

**Решение:** в ядро закладываем **слой предложений** (suggestions) как обычную decoration-модель. Агент или локальная модель предлагает правку, пользователь принимает или отклоняет. Это общая подсистема для ИИ-правок, LSP-подсказок и git-диффа.

### 3.6. Apple Foundation Models (on-device)

Apple выпустила on-device фреймворк Foundation Models (WWDC25): модель работает на устройстве, без сети ([Vioside](https://vioside.com/blog/what-wwdc-25-means-for-your-app)).

**Решение:** это **лучший вариант для офлайн-ИИ**: сводка изменений, переименование, объяснение ошибки, без сети. Проверяем возможности модели в спайке (раздел 5), прежде чем обещать функции.

### 3.7. Что не берём в расчёт

- Совместное редактирование в реальном времени (как в Zed). Противоречит принципу «автономность». Вернёмся, если владелец захочет.
- Удалённая разработка через SSH. Большой объём работы, не приоритет первой версии.
- Встроенный терминал. Полезно, но не в MVP.

## 4. Архитектура

```
┌──────────────────────────────────────────────────────────┐
│  UI: SwiftUI (окна, настройки, панели) + AppKit (текст)  │
│  Liquid Glass: тулбар, сайдбар, панель агента            │
├──────────────────────────────────────────────────────────┤
│  Команды (CommandRegistry)  ←  меню, палитра, клавиши,   │
│                                ИИ-инструменты, тесты     │
├──────────────────────────────────────────────────────────┤
│  Ядро: Buffer (диапазоны, undo-группы), Cursors,         │
│  Decorations (подсветка, LSP, git, предложения)          │
├──────────────────────────────────────────────────────────┤
│  Сервисы:  tree-sitter · LSP-клиент · git (CLI/libgit2)  │
│            · файловый монитор (FSEvents) · восстановление│
│            · ACP-клиент + MCP-конфиг · NSSpellChecker    │
├──────────────────────────────────────────────────────────┤
│  Настройки (TOML/JSON-схема) · Темы dajet/joer           │
└──────────────────────────────────────────────────────────┘
```

**Выбор стека (предложение):**

| Слой | Выбор | Почему |
|---|---|---|
| Язык | **Swift 6** | Нативно, строгая многопоточность |
| Минимальная macOS | **26** | Liquid Glass, NSGlassEffectView (см. раздел 8) |
| UI | SwiftUI для окон и настроек, **AppKit** для редактора | Редактор на AppKit из-за TextKit 2, IME, VoiceOver |
| Текст | TextKit 2; позже — свой Metal-слой, если нужно | Минимум работы сейчас, выход на производительность потом |
| Подсветка | tree-sitter (Swift-биндинги) | Структурный разбор, см. 3.3 |
| LSP | Собственный клиент (JSON-RPC over stdio) | Небольшой протокол, мало зависимостей |
| Git | Системный `git` через `Process`; libgit2 — если нужен быстрый статус | Не таскаем git в бандл |

## 5. Этапы

Оценки грубые и предполагают одного разработчика, работающего на проекте регулярно. Сроки сдвинутся, если появятся решения, которые требуют переделки.

### Этап 0. Решения и спайк (1–2 недели)

- Ответить на вопросы раздела 8.
- **Спайк производительности:** открыть файл 100 МБ и 1 ГБ в TextKit 2; замерить прокрутку, ввод, открытие. Результат решает, нужен ли свой Metal-слой.

- Автосохранение несохранённых буферов и восстановление.

- Цель: ежедневная работа с текстом и кодом без ИИ.

### Этап 2. Полезность (4–6 недель)

- Палитра команд и быстрое открытие файла.
- Git: полоса изменений в гаттере, статус файлов, диффы.
- ~~Импорт настроек и горячих клавиш из Atom~~ — отменено (ADR-0001).
- Настройки в SwiftUI-окне (схема из `config-schema.js`).
- Темы `joer` (5 атмосфер).
- Проверка орфографии через `NSSpellChecker`.

### Этап 3. Языковые сервисы (4–6 недель)

- LSP-клиент: диагностика, переход к определению, подсказки, переименование.
- Символы (outline) через tree-sitter.
- Декорации предложений (suggestions) как общий слой.

### Этап 4. ИИ-агенты (4–6 недель)

- ACP-клиент: запуск агента, сессии, потоковый вывод, запрос разрешений.

- Правки агента показываются как предложения (ревью по файлу).
- Опционально: локальная модель через Foundation Models для резюме и переименования.

### Этап 5. Выпуск (2–4 недели)

- Подпись, нотаризация, DMG.
- Обновления: только вручную или через явную кнопку (принцип автономности). Sparkle не используем без решения владельца.
- Документация для пользователей (на русском и английском), онбординг, пустые состояния.
- Проверка доступности: VoiceOver, клавиатура, «Уменьшить прозрачность».
- Замеры веса и скорости, сравнение с Lite и Zed.

## 6. Офлайн и ИИ: главное противоречие

Принцип Lite: ноль обращений в сеть. ИИ-агенты в основном работают через облако. Поэтому нужно решение, которое владелец должен принять явно:

| Вариант | Что это значит | Плюсы | Минусы |
|---|---|---|---|
| **A. Строго офлайн** | ИИ только on-device (Foundation Models) или локальный агент (например, Ollama на том же Mac) | Принцип сохраняется полностью | Ограниченные возможности |
| **B. Офлайн по умолчанию, облако по выбору** | Сеть выключена, пока пользователь не добавит агента с облачным API-ключом | Гибко, принцип сохраняется как настройка | Нужна явная индикация «есть сеть» |
| **C. ИИ как обычное облачное приложение** | Агенты и API-ключи включены по умолчанию | Максимум возможностей | Отказ от принципа автономности |

**Рекомендация:** вариант B. Редактор не делает сетевых запросов сам. Сеть возможна только тогда, когда пользователь явно запустил внешний агент или добавил ключ. Пункт «Сеть» в настройках показывает, что выключено.

| Риск | Вероятность | Что делаем |
|---|---|---|
| TextKit 2 не тянет большие файлы | Средняя | Спайк этапа 0; при провале — свой Metal-слой (этап 1.5) |
| Liquid Glass меняется между версиями macOS (26 → 27) | Высокая | Тестировать на двух версиях; стекло только для плавающих элементов |
| Нет готовых tree-sitter грамматик для части языков | Средняя | Проверить по каждому языку в спайке; для недостающих — TextMate-подсветка как запасной вариант |
| ACP ещё молод, спецификация меняется | Средняя | Изолировать клиент в модуле `Agents/`; тесты на контракт |
| Объём работы недооценён | Высокая | Этапы 1–2 дают ценность сами по себе; этапы 3–4 можно отложить |
| Потеря совместимости с пакетами Atom | Принято | Пакеты Atom не переносим. Импортируем только настройки и клавиши |

## 8. Вопросы владельцу

Без ответов на эти вопросы дальше идти нельзя. Их можно задать по одному.

1. **Где живёт проект:** папка `native/` в этом репозитории или новый репозиторий?
2. **Минимальная версия macOS:** 26 (Liquid Glass) или 15 (шире аудитория, без стекла)?
3. **ИИ и сеть:** вариант A, B или C из раздела 6?
4. **Первые языки:** 13 языков Lite или только 3–4 (например, JavaScript, Python, Markdown, JSON)?
5. **Пакеты и расширяемость:** делаем ли мы публичное API расширений на этапе 2+, или редактор полностью закрыт?
6. **Имя продукта и бренд:** сохраняем `Atom` в названии (лицензия MIT позволяет) или делаем новое? Палитры `dajet` и `joer` остаются?
7. **Распространение:** только собственные сборки (DMG) или App Store? От этого зависят песочница и доступ к файлам.
